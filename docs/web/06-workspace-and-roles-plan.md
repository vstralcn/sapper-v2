日期：2026-11-02 · 状态：规划已进入实现。本文保留实现前基线与设计理由，当前结果见[实现与验收记录](./07-workspace-implementation.md)。

P0–P3 的本机工作区接入已交付；P4 的 PTY 与真实模型小任务已通过，Linux／HTTPS 与镜像仍待环境验收。下文“现有／当前缺口”描述的是本次开发前的基线，不应当作最新运行状态。

## 1. 规划时的结论与缺口

现有版本完成了基础操作层，没有完成完整工作区与角色协作体验。下一阶段应围绕“将题目所在目录绑定为工作区，在其中启动／接入原 Claude Code 会话，并呈现 sapper 的实际角色与协作”展开。

sapper 主路径使用 Claude Code 完成模型推理和工具执行，sapper 提供事实意图图、任务派发、通信、运行管理与保活。原项目也有其他 CLI 分支，本轮不删除、不替换。

| 用户关心的行为 | 当前实际行为 | 下一阶段补齐 |
| --- | --- | --- |
| 直接使用现有题目文件夹 | 只自动发现受管根目录内已有 `.sapper` 的任务；新建任务要求新目录 | 显式绑定已有目录，不要求搬题、重复上传或重建图 |
| Claude Code 在题目目录工作 | 现有 Web 运行 `cwd` 已是任务目录，但没有专门的 Claude Code 启动／恢复入口 | 一键打开原交互式 Claude Code，显示实际 cwd 和会话身份 |
| 自动使用 sapper 记忆 | 新建任务只初始化图；hooks／说明文件需另行设置，真实 hook 存在已复现故障 | 接入诊断、项目级初始化、真实 hook 子进程测试和注入验收 |
| 体现各角色 | 主要显示 pane／命令和运行方式，仅对原 commander 做基础识别 | 角色列表／树、职责、派发关系、所属题目、模型、会话、报告与操作 |
| 原角色派发选项 | 网页 worker 入口当前固定 TUI，未展示 `--general`、`--p` 等完整配置 | 按原角色与执行形式映射原参数，不减少原功能 |
| 不依赖比赛平台使用 | 原 commander／worker 的平台假设仍保留 | 新增显式本地工作区模式；原比赛模式保持 |
| 对应会话恢复 | Web 记录自己的 run ID，没有系统记录原 Claude 会话 ID | 原生会话 ID、运行状态与 tmux 身份分开记录，精确恢复 |

源码依据：[Web 适配层](../../lib/sapper_web.py) 的 `create_project`、`start`、`panes`；[原 worker](../../docker/commander/worker.sh) 的 `cmd_spawn`；[原角色规则](../../docker/commander/SKILL.md)。

## 2. 工作区如何定义

一个工作区对应一个明确的题目／项目目录：

```text
题目目录/
  题面、代码、附件……            # 已有内容，保持原位置
  .sapper/                     # 原事实意图图，共享记忆的权威来源
  .claude/settings.json        # 项目已有配置，启用 sapper 时只合并相关 hooks
  AGENTS.md / CLAUDE.md         # 按现有文件和 CLI 能力接入，保留用户正文
  outputs/                    # 示例产物目录；已有目录布局不强制改名
```

Web 独立保存工作区绑定、角色、会话与运行记录。图继续使用原 JSON，不将目录中的资料拷进新的权威数据库。目录绑定不会自动启动 agent、改写题目内容或安装 hooks；用户在网页点击“启用 sapper／启动会话”时执行对应的项目级操作。

### 2.1 入口

1. **打开已有目录**：填写／选择执行环境中的目录，预览真实路径和已有文件，显式绑定。
2. **新建工作区**：保留当前的新目录与上传入口。
3. **接入已有会话**：发现相关 tmux／Claude 会话，经用户选择后关联，不重新启动。

本机路径指当前执行机路径。服务器上的浏览器文件上传是导入资料，不能把客户端本地路径当作服务器可访问目录。目录选择在管理员明确配置的可访问根目录内进行；超出根目录需要显式配置，不因填写字符串自动扩大访问范围。

绑定使用稳定工作区 ID 和规范路径，不再仅靠扫描深度或目录名称维持身份。已有 `.sapper` 原样接入；同图 worker 的别名目录归入同一工作区。

### 2.2 推荐的会话与目录规则

- **主执行者**：默认 cwd 直接是题目目录，使用原交互式 Claude Code，不要求用户自行输入一长串启动命令。
- **指挥官**：保持原职责，专注读板、判断、派发与交接。其控制目录可独立于题目资料目录；跨题目指挥官关联一个工作区集合，不在每个题目下重复启动。
- **额外 worker**：保留原“一 agent 一会话目录、共享事实图”的机制。工作目录与题目资料目录分别展示；通过明确路径／原 CLI 支持的附加目录访问同题资料，输出分目录保存。
- **已有会话**：不搬动 cwd，不改变原目录和恢复方式，先保存真实关联信息。
- **同目录并行**：如果用户明确选择多个会话共用题目根目录，每个会话必须绑定独立原生 ID；文件写入需分工并显示并行修改，不能把会话分离宣传为文件强隔离。

因此，“工作区是题目目录”是产品入口；不要求所有角色都挤在同一个 cwd。主执行会话满足直接在题目文件夹工作的需求，其他角色保留原协作与恢复约束。

当前官方 CLI 支持指定会话 ID、按 ID 恢复和添加访问目录；`--continue` 指向当前目录的最近会话。新接入路径优先精确 ID 恢复，旧路径在未适配前继续遵守其独立 cwd 约定。[Claude Code CLI 官方文档](https://code.claude.com/docs/en/cli-reference)

### 2.3 启动流程

```text
绑定题目目录
  → 检查目录、原 CLI、现有图、项目说明和 hooks
  → 按需启用项目级 sapper 接入
  → 选择主执行／协作模式和原模型配置
  → 分配并记录原生 Claude 会话 ID
  → 在明确 cwd 中启动原 CLI
  → 网页显示文件、终端、角色、共享图与输入回执
```

启动时保留原工具、MCP、skills、模型与权限选择，不通过 `--bare`、替换系统提示词或改写工具集合来简化 agent。任务资料不需要重新贴给模型；通过工作目录和现有工具读取。

## 3. 角色应如何体现

原 sapper 的角色与 Claude Code 内置 subagent 类型不是同一层概念。网页呈现原 sapper 的实际分工，不把所有角色替换成另一套 Claude Code Agent Teams／SDK 编排，也不要求每题固定启动全套角色。

| 角色／组件 | 原本职责与依据 | Web 应提供的表现 |
| --- | --- | --- |
| 指挥官 Commander | 原 commander 规则：读板、选择、派发、调整资源、维护交接 | 工作区范围、派发树、任务决策摘要、状态与原会话入口 |
| 将军 General | 原 `--general` worker：攻坚并可派发子队伍，仍参与实际执行 | 角色标签、父指挥官、子 worker、任务说明、报告与产物 |
| 侦察兵 Scout | 原 commander 的限时侦察任务，常用 `--p` 与侦察说明 | 职责与时限、侦察结果、后续接手者；不按模型名称猜角色 |
| 士兵／执行者 Worker | 原默认执行 worker，完成分配的解题工作 | 当前任务、模型、cwd、原会话、关联意图与成果 |
| 验证者 Verifier | 原 `dispatch verify`／可选验证步骤，也可被明确派为任务 | 按实际存在的步骤或会话展示；不虚构长期在线的验证进程 |
| 看门狗 Watchdog | 原脚本保活、轮换、预算与异常处理 | 服务状态、最近事件与作用范围；不计为消耗模型的角色 |
| 通信／其他自定义职责 | 历史报告中的涌现分工，不是所有任务都内置的固定进程 | 指挥官确实分配后记录其自定义角色；默认不强制创建 |

`TUI`／`-p` 是执行形式，`--general`／侦察任务是角色或职责，模型档位是配置，三者分别展示。改变模型不能自动把士兵标为将军。

### 3.1 角色记录

建议的 Web 侧记录字段：`agent_id`、`role`、`role_source`、`parent_agent_id`、`workspace_id`／工作区集合、`mission`、`execution_mode`、`cwd`、`claude_session_id`、tmux 标识、模型配置快照、关联意图、报告和产物引用。

- Web 发起的原角色启动保存真实选择与参数。
- 指挥官在后台通过原 worker 脚本创建的 agent，也必须进入登记与展示，不能只登记网页按钮创建的会话。
- 在原启动点增加轻量记录，不改变指挥官的解题与派发策略；派发者身份向下传递，用于恢复父子关系。
- 对已有 pane，只在有可靠记录时确定角色；否则显示“角色未标注”，允许用户显式标注并记录来源。
- 角色归属必须与其原生会话关联。tmux pane 被重用或进程重启时，不沿用旧角色状态冒充新进程。
- 派发关系属于 sapper 层，不强求每个 worker 都是 Claude Code 内置 subagent，保留原独立 CLI 会话机制。

### 3.2 界面

工作区首页优先展示：顶部实际目录与会话状态，左侧题目文件树，中间原 Claude Code 终端，右侧角色／派发树。共享记忆、报告和产物保留独立入口。

每个角色可查看职责、指令、模型、实际 cwd、关联会话、最后输出、共享图贡献和子任务；可将补充信息发给指定角色。页面不以终端几秒无变化推断“思考中”“卡死”或“等待输入”，没有可靠信号时显示“进程存活／最近输出时间”。

主要按钮变为“打开 Claude Code”“恢复此会话”“启动原指挥官”“派发原 worker”；目前的 `auto/dispatch/自定义命令` 保留为高级操作。

## 4. 规划时发现的接入问题（现已修复）

### 4.1 Hook 导入失败：已复现

[lib/sapper-hook.py](../../lib/sapper-hook.py) 第 39 行仍为 `import fg`。当前仓库没有对应模块，本机执行：

```bash
python3 lib/sapper-hook.py sessionstart
```

返回 `ModuleNotFoundError: No module named 'fg'`，退出码 1。这是当前本机源码路径的实测，不延伸宣称所有旧镜像都已验证同一故障。

### 4.2 Hook 上下文字段：需对齐并验证

同文件目前为 `UserPromptSubmit` 输出 `contextForClaude`；当前官方文档列出的上下文输出字段为 `hookSpecificOutput.additionalContext`。应对照目标 CLI 验证并修正，不能只修复导入就宣称自动注入可用。[Claude Code hooks 官方文档](https://code.claude.com/docs/en/hooks#userpromptsubmit-decision-control)

### 4.3 指令文件的读取：需检查实际配置

原 setup 会生成 `AGENTS.md`，但是否自动加载受 Claude Code 版本、已有 `CLAUDE.md` 与设置影响。启用工作区时应检查现状，必要时以兼容的受管导入连接原说明，不覆盖用户说明、不修改全局配置。[官方指令文件规则](https://code.claude.com/docs/en/memory#agentsmd)

本机核对到的 CLI 版本为 `2.1.316`，帮助中存在 `--session-id`、`--resume`、`--add-dir`。容器与服务器版本需分别检查，不能依据本机结果自动升级原镜像。

此前 57 项通过的测试覆盖原图／CLI 和基础 Web 路径，未执行这条真实 hook 脚本，也不构成所有原角色完整呈现的证据。原测试结果仍有效，但验收范围应按实际路径区分。

## 7. 验收场景

1. 选择一个已有题目目录，不复制资料；在网页打开 Claude Code 后，实际 `pwd`、文件内容和图位置都能核实。
2. 本地与服务端路径在界面明确区分；无权限／超出配置根目录时给出具体原因，不把目录不合法显示为模型错误。
3. 已有 `CLAUDE.md`、`AGENTS.md`、hooks 与 MCP 配置保持；重复启用不重复追加或覆盖。
4. 真实 hook 脚本以事件 stdin 中的 cwd 找到该题图，输出合法字段；无图目录不继承父题记忆；与旧模块名相关的失败被回归捕获。
5. 两个 Claude 会话在同目录启动时，精确恢复各自的 ID；一个会话仍存活时不重复启动，未知身份不使用“最近会话”猜测。
6. 将军派出的子 worker、侦察任务与验证步骤按真实职责展示；未知旧会话保持未标注，watchdog 不混计为 LLM agent。
7. 两题同时工作时，角色、模型绑定、原生会话、图、资料与停止对象不串题；同题辅助 agent 能读取指定资料并回写同一原图。
8. 主执行者在题目根目录工作；辅助角色沿用自己的目录与恢复方式，页面展示差异，不把目录划分当作安全沙箱。
9. Web 重启／断网不结束原会话；恢复与停止对照真实进程，watchdog 不将明确停止的对象误当异常反复重启。
10. 原比赛入口、原命令和现有工具仍可使用；新增本地模式不请求比赛平台，不擅自提交外部结果。
11. 用假 CLI 验证参数、cwd、角色和会话映射，再用已配置的真实 Claude Code 完成一个小型可复核任务，验证实际读取资料、使用工具和保存进度。
