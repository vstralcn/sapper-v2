# 会话恢复后不自动继续：待修复规划

日期：2026-11-02。状态：已确认缺陷，待实施。优先级：高（核心工作区交互）。

## 1. 已验证现象

在 Geek2026 工作区对一个正在运行的 General 执行“停止 → 恢复此会话”后：

- 原 Claude 会话 UUID 被正确复用，新进程和 tmux pane 正常建立。
- `sapper-native-roles/1`、全局上下文和原会话历史均已加载，角色提示词修复本身生效。
- Claude Code 恢复后停在交互输入框；`auto mode on` 只表示 Claude Code 的权限／交互模式，不表示任务循环正在推进。
- 终端提示旧后台 shell 未在上一会话结束前完成。该进程已随停止操作结束，恢复聊天历史不会恢复操作系统后台进程。
- 工作区的“进程存活”只证明 TUI 仍在运行，不能证明模型正在解题。
- 已存在的子角色可能在任务完成后仍停留在输入框并占用并发名额；本次观察到的子角色创建早于主角色恢复，不能当作新版策略恢复后主动派发的证据。

本项与“角色是否获得原生派发提示词”是两个不同问题：前者是恢复后是否产生新一轮用户输入，后者已经由 `sapper-native-roles/1` 修复。

## 2. 根因

当前 `Workspaces.create_session()` 对交互式旧会话只构造：

```text
claude --resume <uuid> ... --append-system-prompt <当前角色与全局上下文>
```

实现仅在“新建会话”或 `print` 模式时把 mission 作为位置参数传给 Claude。交互式恢复没有新的用户消息，因此 Claude 正确恢复到等待输入状态。页面按钮名“恢复此会话”没有解释“只恢复终端和历史，不自动继续任务”，容易让用户误以为恢复后会立即执行。

后台 shell 属于旧 Claude 进程树。停止角色会结束该进程树；恢复只能恢复 Claude 会话记录，不能也不应尝试复活旧 PID 或盲目重放最后一条命令。

## 3. 目标行为

Web 应明确提供两种恢复语义：

1. **恢复并继续（推荐默认）**：复用原 UUID、加载当前角色提示词，然后发送一条明确的新用户消息，触发下一轮工作。
2. **仅恢复终端**：保持当前行为，只打开历史和输入框，适用于用户希望先人工检查的情况。

“恢复并继续”的默认续作消息应说明：

- 继续原角色保存的 mission，不重新初始化任务或事实图。
- 先读取当前共享图、工作区文件和策略看板，再决定下一步。
- 把上一会话未完成的后台命令视为“状态未知／已中断”，先检查产物与副作用；不得因为历史里显示 running 就假定它仍在运行。
- 不盲目重放可能不可逆的命令、平台启动／关闭、提交或外部操作。
- 继续遵守原 mission 的提交授权、目录、预算和角色边界；恢复动作本身不扩大权限，也不强制派发子角色。

用户可在恢复前补充一段本次续作说明；该文本作为本轮用户消息，不覆盖基础职责或原 mission。

## 4. 实现规划

### P0 — 恢复参数与状态模型

- 恢复接口接受显式 `resume_mode=continue|terminal_only`，拒绝未知值。
- 为继续模式生成短而确定的续作消息；保存 `resume_mode`、消息摘要和发送时间，不保存密钥。
- 保留 UUID、cwd、模型快照、父角色、工作区范围和 `sapper-native-roles` 版本检查。
- 清理恢复成功记录中容易误读的旧停止时间，保留历史 run 的停止证据。

### P1 — 原 CLI 调用

- 验证当前 Claude CLI 支持 `--resume <uuid> <continuation-message>`，并证明消息只进入一次。
- 如果所用 CLI 不能在启动时携带续作消息，则在 pane 确认可输入后通过现有终端发送机制发送；不得同时走两条路径。
- 请求重试、页面重复点击和网络重连必须幂等，不能产生两条“继续任务”消息或两个恢复进程。

### P2 — Web 交互

- 将主操作显示为“恢复并继续”，旁边提供“仅恢复终端”。
- 恢复确认区展示：原角色、UUID、当前基础职责版本、原 mission 摘要，以及“旧后台任务不会恢复”的提示。
- 允许填写本次续作补充；默认文本不要求用户复制角色策略。
- 恢复后角色卡区分“进程存活”和“已发送续作消息”。没有可靠模型事件时仍不显示“正在思考”。

### P3 — 子角色与容量提示

- 看板继续区分进程、图进展和终端状态。
- 对已完成但 TUI 仍停在输入框的子角色，只提供“可能等待输入／请检查并回收”的可核实提示；不得仅凭提示符自动杀死。
- Commander／General 仍按原策略负责 `peek → harvest → kill`。Web 不新增自动清理策略，也不把旧子角色算作恢复后新派发。

## 5. 验收条件

1. 交互式角色选择“恢复并继续”后保持原 UUID，并在同一恢复 run 中恰好收到一条续作用户消息。
2. 新基础职责和最新全局上下文仍被追加；原 mission、提交授权和模型配置不被静默修改。
3. 选择“仅恢复终端”时不发送任何新用户消息，终端明确显示等待人工输入。
4. 旧后台 shell 不会被宣称为已恢复，也不会自动重放；续作角色先检查当前产物和图证据。
5. 两次相同请求或浏览器重连不会创建重复 pane、重复续作消息或重复外部操作。
6. 恢复前后父子关系、共享图、工作区范围和历史 run 保持可追溯。
7. 使用假 CLI 覆盖参数／幂等测试，再用真实 Claude Code 的可逆小任务验证“中断 → 恢复并继续 → 检查产物 → 完成”。
8. 浏览器检查两种恢复入口、说明文字和状态展示；不以截图或“进程存活”替代实际消息与结果证据。

## 6. 本项不做

- 不复活旧操作系统 PID，不重放未知后台命令。
- 不因恢复而自动提交 Flag、启动／关闭平台实例或扩大目录／网络权限。
- 不把 `auto mode on` 当作 Sapper 自主循环状态。
- 不强制恢复后派兵；是否协作仍由角色基础职责、当前看板和任务条件决定。
- 不自动停止看似完成的 TUI 子角色，除非后续获得可靠完成事件或用户明确操作。

## 7. 临时使用方式

修复完成前，执行“恢复此会话”后需要通过“补充说明”或终端手动发送一条继续消息，例如：

```text
继续原任务。先读取共享图和当前文件；把上一会话未完成的后台任务视为已中断，检查现有产物后再决定是否重做。遵守原任务的提交授权，并按当前角色职责判断是否需要协作。
```

该临时操作会触发新一轮执行，但不会恢复旧后台进程。
