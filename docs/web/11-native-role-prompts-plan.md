# Web 角色基础提示词：原生策略对齐规划

日期：2026-11-02。状态：核心修复已实施。新建／显式恢复的 Web 角色使用 `sapper-native-roles/1`；正在运行的旧角色不被改写。

2026-11-07 更新（`sapper-native-roles/7`）：Web 主 agent 统一负责本工作区的用户对话、澄清、派单和纠偏，调度策略改由模型根据证据与资源判断。下文的四分钟侦察、固定升级时间表及动作配额属于历史实现；当前入口、消息和 watchdog 联动见 [终端、文件与 Agent 状态](17-main-agent-chat.md)。

2026-11-05 补充（`sapper-native-roles/6`）：核查到一个以 `commander` 和 `/5` 基础职责启动的会话仍直接执行题目任务；不是漏传 `--append-system-prompt`。原通用 SessionStart／UserPromptSubmit hook 未区分指挥官与执行者，是本次修复的提示冲突点，不能据此断言模型越界只有这一个原因。

- 指挥官基础职责增加中文说明：用户的“完成题目”是组织执行者完成；平台查询、附件分析、解题脚本与提交交给将军或 worker，派发失败不转为亲自解题。
- 两类 hook 使用启动环境中的受管身份定位 Web 角色记录，并核对工作区与共享图；对指挥官注入同源职责，替换通用执行引导。普通角色和未受管会话保留原流程；不从图文本推断角色。
- 已运行的受管指挥官在下一次相应 hook 执行时即可读到本次提醒，无须改写会话快照或主动发送消息。常驻 Web 后端重新加载代码后，新建／显式恢复使用 `/6` 基础职责；当前进程的系统提示词不会被追溯替换。
- 设计约定：所有 Agent 保留原有工具能力，包括 Bash；角色通过职责、任务目标与交付上下文区分。此次只修复角色提示和上下文注入，不增加按角色拦截工具的机制；工具能力保持可用符合本次要求，不属于待补缺口。自动检查验证实际注入与派发链路，不保证任意模型必然遵守。

## 0. 实施结果

- 新增 `lib/sapper_roles.py`，集中定义可追溯的 commander／general／worker／scout／verifier／custom 基础职责；Web 创建与后台 `worker.sh spawn` 共用同一渲染入口。
- commander 获得原 4.6／4.10 的条件派发阶梯：陌生任务 4 分钟 scout、不同角度二线、General 升级、结果读取与回收；不改成固定人数或无条件派兵。
- general 获得原 `general_mission()` 的 5 分钟侦察／验证小队能力、同时最多两个、`list/board → peek → 图证据 → kill` 的完整闭环。
- 普通 worker／scout／verifier 不显示派发语法，也不默认获得子角色控制权。
- 工作区 `board --json` 现在返回真实图摘要、Flag 状态计数、HELP／REPORT、开放意图、角色／父子关系和最近图活动；缺失全局预算标为 `null`，不从终端重绘推断卡死。
- 创建角色窗口显示职责摘要、来源、版本和实际追加提示词；角色记录保存版本、来源与 SHA-256 摘要。
- CLI 不支持 `--append-system-prompt` 时在创建任何角色目录前拒绝启动，避免出现“角色已运行但没有基础职责”的静默降级。

自动检查：完整 `python3 -m unittest discover -s tests -v` 共 109 项通过；Python／JavaScript／shell 静态检查与 `git diff --check` 通过。浏览器已核对 General 摘要、来源版本和实际提示词。真实模型是否在某道题上满足条件仍属于模型决策，不能以脚本测试承诺每次必然派发。

## 1. 目标与范围

Web 创建角色时默认加载与原 sapper 职责一致的基础提示词。用户填写的是具体任务，不应依赖用户再次解释将军如何派兵、指挥官如何读板。模型仍按原策略判断是否需要协作；不新增固定开局人数、强制全角色启动或新的调度循环。

“一致”分为两部分：职责、条件、行动顺序和原约束保持；本机路径、工作区标识、通信参数等按实际运行环境映射。原版的 TSecBench URL、容器数量、凭据变量及自动提交授权不直接套用到通用工作区。当前用户任务中的“提交前询问”继续生效。

保持原 CLI、Claude Code 工具、图格式、模型选择、hooks、权限选项与会话机制。除共享提示词来源所需的小范围提取外，不重构原调度器。

## 2. 已核实的基线与缺口

| 原生来源 | 原有行为 | 当前 Web 缺口 |
| --- | --- | --- |
| `docker/commander/entrypoint.sh` 的 bootstrap；`docker/commander/SKILL.md` | 指挥官读取交接文件、读板、判断、派发／沟通／回收，循环至预算结束 | `role_prompt()` 只有简短职责与工具入口，未接入完整作战流程 |
| `docker/commander/SKILL.md` 4.6、4.10 | 陌生题先短时侦察，按难度派士兵／将军；停滞时不同角度、升级、暂存；已有同类证据时可跳过重复侦察 | 未映射这些条件和升级顺序 |
| `docker/commander/worker.sh` 的 `general_mission()` | 将军自己解题，可派同题短时小队做侦察／验证／fuzz；约 5 分钟、最多 2 个，查看结果、收集、回收 | 只剩“可按需派发”，缺少具体小队使用与回收说明 |
| 同文件 `default_mission()` | 士兵推进当前题，记录带类型的事实、读取知识库、共享同题图，通过 HELP／REPORT 交接 | 未完整传入士兵的基础任务规约 |
| `docker/commander/SKILL.md` 4.4、4.10；`templates/verify.md` | 短时侦察与最小证据核验 | Web 的 scout／verifier 目前是简短描述，未标明原生依据 |
| `docker/commander/SKILL.md` 4.7、7.0 | 默认由执行者提交；提交受阻时可派约 3 分钟提交小队 | 先前讨论的“提交专员”并非必须新增的原生常驻角色 |
| `lib/sapper_workspace.py` 的 worker `board/list` | 当前主要返回登记角色 JSON | 缺少原指挥官判断所需的图进展、Flag 状态、HELP／REPORT、预算等信息 |

另有两项容易混淆的地方：

- 显示名称不决定角色。当前实际任务里“指挥官1”的 `role` 为 `general`，所以应执行将军职责。
- 原 `auto --verify` 是调度步骤，不等于独立的 verifier 进程。`templates/command.md` 的 JSON 决策循环与 tmux 指挥官作战手册也不是同一条执行路径，不能混合注入。

原仓库还存在部署注释与正文不完全一致的情况，例如 worker 的 ALL-IN／MIXED 模型说明及部分过时帮助文本。规划不自行选择一套新模型策略：原执行路径保持实际参数行为，Web 明确选定的模型配置继续优先；建立来源差异记录，不把供应商名称和配额推测写成通用角色规则。

## 3. 提示词来源与复用方式

### 3.1 采用同源职责模板，避免再维护一套角色文案

拟增加 `lib/sapper_roles.py`，统一描述角色来源、渲染参数和版本。将原 `general_mission/default_mission` 的职责正文提取到共享文件，原 shell 函数仅改为调用同源渲染，保留原函数入口、变量、命令和行为。先保存原输出对照，再提取；不通过正则在运行时猜测 shell 函数内容，也不执行 shell 来“抓取”提示词。

指挥官的作战依据继续是原 `docker/commander/SKILL.md`：提取／引用适用章节，记录明确映射关系，不另写一套升级条件。原启动 bootstrap 的“先读交接，再读板和行动”保留，并替换为真实可访问路径。

共享文件的具体位置在实施时与现有打包结构一起确定，优先放在原 commander 目录中，避免混入已有 `reason/explore/verify` 单步模板。若原脚本输出无法证明等效，该提取不得合入。

### 3.2 角色映射

| Web 角色 | 默认职责来源 | 保留的差异 |
| --- | --- | --- |
| 指挥官 commander | 原 bootstrap、ROLE、LOOP、调度决策表、交接与失败处理 | 不亲自解题；按可用工作区和实际预算协调 |
| 将军 general | 原 `general_mission()` | 亲自攻坚，按需派同题短时小队；不强制开局建两个助手 |
| 执行者 worker | 原 `default_mission()` | 完成分配的题目／步骤，记录证据并报告；不获得全局调度职责 |
| 侦察兵 scout | 原短时 scout 任务约定 | 是原小队职责的显式标签，不新增另一种调度引擎 |
| 验证者 verifier | 原短时 verify 小队约定与 `verify.md` 的核验职责 | TUI 使用职责与证据要求；原 dispatch 的 JSON 返回格式仅留在原 dispatch 中 |
| 自定义 custom | 原共享图与工具使用规约，加用户职责 | 不擅自赋予指挥官／将军权力，也不额外追加升级策略 |

### 3.3 允许的适配

- `/opt/sapper/.../worker.sh`、`/work/runs`、交接文件路径 → 本机实际入口、已授权工作区与角色目录。
- 原 `<code>/<pane>` → 现有工作区 ID／名称、agent ID 与真实 pane，给出当前适配入口真正支持的命令。
- 平台地址和实例状态 → 已配置平台能力；平台信息不足时明确未知，不编造接口或回退 POST。
- 原实际预算／并发约束 → 当前运行记录和执行形式。TUI 的任务时间说明不能冒充脚本硬超时，没有全局预算时不虚构 8 小时比赛或倒计时。
- 自动提交、平台关闭与凭据轮换 → 仅在原执行路径或本任务已明确授权且有对应能力时保留；普通工作区不凭提示词自动接管。

上述差异要在映射表中逐条注明理由。4 分钟侦察、5 分钟小队、最多两个小队等原有约定按其原条件保留；不改成无条件派发或 Web 新增调度器。

## 4. 启动、派发和提示词组成

统一渲染用于网页新建角色和 `worker.sh` 工作区分支的后台派发，避免两个入口使用不同基础职责。首次启动与恢复都能核对加载版本。

组成保持清楚：

1. 原 Claude Code 自身系统提示词与工具集合保持。
2. 追加同源角色基础职责及必要的路径／能力映射。
3. 沿用已有全局上下文注入；工作区图、hint、任务资料仍通过原接入读取。
4. 用户任务作为具体 mission；不会覆盖或删除基础职责。显式任务授权优先，图和目标输出继续作为数据处理。

优先使用现有 `--append-system-prompt`，不使用替换系统提示词的方式。如果 CLI 缺少该能力且不能证实其他方式能等效加载，启动前明确报告，不默默退回当前一句话职责。

角色记录增加基础提示词版本、来源和实际渲染摘要，便于诊断“加载了什么”。存储不含 API Key。需要预览时显示实际渲染内容，不只显示一个模板标题。

## 5. 最小看板适配

仅补齐原角色策略需要的观察数据，不新建调度数据库，不引入自动升级评分。

- 保留现有 `worker.sh list/board` 调用兼容；用兼容字段或明确的原生策略看板入口提供完整信息，避免破坏已使用的 JSON 调用方。
- 复用现有图读取／`_board_summary` 语义，补齐各工作区事实摘要、未完成意图、Flag 本地状态、HELP／REPORT、角色及父子关系、最近图活动时间。
- 区分“进程仍活着”“最近有图进展”和“终端持续重绘”。后两者不能互相代替；不能把没有图更新直接断言为模型卡死。
- 显示已知预算、并发上限和可派发范围；缺失数据标为未知／未配置，不伪造平台实例数或业务提交回执。
- 同题小队结果通过原图与 peek／消息收集，保留原先回收小队的做法。不会因为任务短时退出，就自动判定失败并重派。

这些信息是原决策表的输入，是否派发及升级仍由原角色策略和模型决定。

## 6. Web 交互调整

- 创建窗口选择角色后显示其基础职责摘要、来源与可展开预览；更换角色时更新预览，保留用户已填写的 mission。
- “角色名称”和“实际职责”分别展示。例如“指挥官1 · 将军”，名称不会暗中修改角色类型。
- 任务说明只要求填写目标、资料、平台 CLI、预算和提交授权等任务信息，不要求用户复制原角色规则。
- 后台派发也显示相同的实际职责、基础提示词版本、父角色与运行结果。
- 不增加默认并行人数、自动提交开关或大型提示词编辑系统；不把本次工作变成新协作策略配置产品。

正在运行的角色不被中断或追加新任务。新角色使用新基线；旧角色标明旧版／来源未记录，不假称已更新。用户希望旧任务采用新基线时，在明确的重新启动／恢复操作中提示变化，并保留原图与原生会话身份规则。

## 7. 实施顺序

| 阶段 | 工作内容 | 验收条件 |
| --- | --- | --- |
| P0 来源冻结 | 记录原职责、策略条件、命令接口、平台依赖和历史差异；建立输出对照 | 每条默认策略能追溯到原文件；没有推导出新规则 |
| P1 同源模板 | 提取角色职责、增加统一渲染；原 shell 入口保持 | 原路径默认输出／参数对照通过，只有列明的环境映射有差异 |
| P2 工作区接入 | 网页／后台派发复用渲染，记录来源版本；明确恢复规则 | 不手动补角色规则也能加载完整基础职责，mission 不覆盖它 |
| P3 看板补齐 | 接入原策略所需图进展、报告、预算和角色状态 | 原决策表所依赖的输入有真实来源；缺失值不被伪造 |
| P4 页面呈现 | 创建预览、实际角色标签、来源和旧会话提示 | 名称与职责不再混淆，预览和实际启动一致 |
| P5 集成验收 | 原 CLI 回归、隔离 tmux、浏览器和一条受控协作任务；更新使用文档 | 角色加载、派发、结果回收与停止可验证，原循环未替换 |

同步检查 commander／Web 镜像和安装后的路径是否带齐共享文件；当前 Web Dockerfile 只复制三个 commander 脚本，新增来源文件时必须同步复制。镜像构建仍需有 Docker 环境才能声明通过。

## 8. 验证方法与完成标准

1. 原版输出基线与同源提取后的渲染对照，覆盖路径含空格、任务内容和变量替换。重点保证引号、范围、预算与提交语义不变。
2. 新建、后台派发、恢复的实际 CLI 参数检查：同一角色同一基础职责，父身份／图／模型继承正确，不替换原工具或权限。
3. 条件对照：陌生题侦察、已有同类证据跳过重复侦察、将军小队上限与回收、无需并行的任务继续单角色；不能以“所有任务都产生士兵”作为成功条件。
4. 受控图和 tmux 验证：将军派出限时助手、助手写共享图、主角色查看结果并回收；预期派发失败可见原因，不默默丢失子任务。
5. 提交相关测试仅用本地假平台／CLI：当前“先询问”任务不能因为加载原版自动提交文字而变为直接提交。原 TSecBench 路径行为保持。
6. 浏览器检查角色预览、名称／实际职责、父子派发与状态。使用真实 Claude 的受控小任务验证加载与协作链路；脚本假模型只能证明入口和参数，不能充当模型自主决策证明。

完成声明限于：Web 默认加载有来源的原生职责、所需运行信息可读、入口一致、相关原 CLI 行为保持且集成链路经过验证。不会承诺任意模型在每道题上都会作出相同派发决定。

## 9. 本轮明确不做

不增加常驻提交官、通用提交队列或平台下载／提交连接器；不修改当前任务的提交授权；不硬编码“必须创建两个士兵”；不改动正在进行的 Geek2026 任务；不重写原 agent 工具循环、供应商轮换或 watchdog 策略。

这些能力如后续单独开发，应继续与原角色职责区分，不能夹带在基础提示词对齐中。
