## 一句话记忆

**把设计重心从单个 Agent 的聪明程度，扩展到可协作、可交接、可积累、可恢复的组织能力：以创建、通信、外部历史为基座，让角色和策略围绕实际任务演化，再用资源调度和可靠运行支撑它。**

文章用“个体可以消亡，文明必须繁衍”表达连续性。工程上可取的解释是：在用户授权的目标、时限和资源范围内，任务状态与已验证知识不应随某个会话退出而丢失；它不是无限运行、自行扩权或对抗用户停止的要求。

## 核心思想及工程启发

### 1. 组织能力与模型能力一起设计

文章主张：单纯增强一个模型，未必能得到分工协作带来的整体能力；“组织起来的模型”可能形成新的能力形态。

工程启发：遇到复杂任务时，先判断瓶颈是推理能力、上下文、信息共享、协调、资源还是运行可靠性，再决定升级模型、拆分任务或改造 harness。多 Agent 有通信和协调成本，简单任务仍可由单 Agent 完成；角色数量不是优化目标。

### 2. 基座优先：创建、通信、历史

| 基础能力 | 原文实现示例 | 应保留的设计含义 |
| --- | --- | --- |
| 创建个体 | 通过 tmux 启动新的 AI 会话 | 在既有授权与预算内按任务需要创建、替换执行单元 |
| 个体通信 | 向对方 tmux 输入框投递内容 | 能传达任务、反馈、线索和交接信息，并能观察投递与实际处理的区别 |
| 外部历史 | 事实／意图图，标题、摘要、证据三层 | 共享知识独立于单个会话，支持逐层检索和后续接班 |

tmux 是文章的实现选择，不是架构原则本身。人类智慧是额外的关键输入：识别主要问题、确定方向、评价结果和推动迭代。

### 3. 记忆要分层，结论要能回到证据

文章将早期单字符串记忆改为“标题 → 摘要 → 证据文档”：先用少量上下文定位，再按需深入，降低长记录的读取成本。

工程启发：

- 标题支持快速发现；摘要保留结论、状态和适用条件；证据层保留复现材料与来源。
- 区分已验证事实、待验证假设、失败尝试和下一步意图。一个 Agent 说过的内容不能自动成为事实。
- 分层有助于查证，**不会自动消除错误事实的传播**。关键结论出错时，应重新检查依赖它的判断；相关校验机制需要单独设计和验证。
- 把原始长日志留在证据层，默认注入与当前任务相关的摘要，避免每轮读取全部历史。

### 4. 让分工回应瓶颈，保留策略调整空间

作者描述了运行中逐渐形成的指挥官、将军、士兵、侦察兵和通信兵。其价值在于解决具体问题：宏观调度、长链任务协调、具体执行、低成本探路和集中处理提交。

工程启发：角色是对责任和瓶颈的回应，不必在所有任务里复制同一套兵种。能先侦察再分配资源，也能在重复错误或协调成本过高时调整分工。策略探索可以交给 Agent；目标、权限、资源上限、停止语义和结果校验仍需明确。

原文反对把所有行动写成僵硬步骤。这里应保留的是“减少无证据的流程束缚”，不能推导成所有 skill、工具说明和约束都有害。必要说明是否有效，要看它解决了什么实际问题。

### 5. 会话可以替换，工作必须能接续

文章中的长链任务采用将军协调、士兵轮换和共享图接班；压缩前写交接文档，压缩后读回。

工程启发：交接应覆盖目标、已确认事实及证据、尝试过但失败的路径、当前子任务、下一步、资源与时限、待决策事项。替换个体和压缩上下文是否有效，要看接班者能否继续产出，而不是只看会话是否启动成功。

正文的 85% 写交接、90% 自动压缩是作者描述的具体机制，不能作为跨模型、跨 CLI 的固定阈值。模型窗口、事件接口和压缩行为应以实际环境为准。

### 6. 可靠运行是能力的一部分，策略与保活职责分开

文章运行结构是：指挥官读板与派单、军团执行、纯脚本 watchdog 保活。额度耗尽、OOM、崩溃等运行故障可能使策略再好的系统也无法完成长任务。

工程启发：优先补齐真实故障路径上的恢复能力，区分基础设施故障与任务策略停滞。监控器负责观测和既定恢复机制，策略由负责决策的 Agent 承担；恢复还应保留用户停止、等待用户、完成和预算耗尽等终止条件。

进程存活、继续消息已发送、模型有响应、实际恢复任务是不同层次的证据。不能仅凭“重启成功”宣称任务恢复，也不能凭沉默就判定需要重启。

### 7. 经济制度：按任务难度和边际收益配置资源

文章采用模型分层：指挥官、将军使用较强模型，士兵、侦察兵使用较轻模型。先侦察，再决定是否投入更昂贵的推理与协调资源。

工程启发：为不同任务选择合适模型和投入，允许根据新证据升级、替换或停止路线。模型名称只是历史配置示例，不能直接作为当前推荐或可用性依据。

评价优化时，同时看已验证结果、成功率、耗时、模型／工具费用、重试及协调开销。Token 数量只是其中一个维度；不同供应商的 token 也不等价于同样成本。

### 8. 稀疏而相关的知识，比默认灌入大量材料更有用

文章强调精简的经典方法、通用策略和可复用经验，避免查询一次就消耗大量上下文。

工程启发：默认检索少量相关知识，再按需下钻；把已验证的共性打法转成带前提、证据和失效条件的简短提示或手册。迁移依据应是结构与条件相似，不能只因题名或表面相似就复用结论。

### 9. 调度与迭代应围绕有效进展

文章描述了先获取简单成果、并行投入难题、受阻后回收已有部分进展，以及对长期无新产出的执行者调整策略。这些适用于有时间限制和多目标收益的场景。

工程启发：观察新证据、可验证产物和离目标的距离，而不是消息量、运行时长或 Agent 数量。连续尝试不再增加有效信息时，改变假设、路线、资源或任务分配。竞赛中的“先易后难／残值收割”需要根据真实任务优先级取舍，不能覆盖用户的关键依赖和必做目标。

作者将“运行探索出的机制，由人类帮助固化以省去下次探索”视为重要迭代方式。值得保留的是有证据的经验沉淀；单次表现和重复症状不足以证明通用规律，持久规则仍需相应证据和写入授权。

## 如何看待文章中的证明力度

- **作者报告的竞赛结果**：634 队中第一、80.18 分、8 小时无人值守；与第二名同为 85 个 flag，快 25 秒；10.3 亿对 45 亿 token。这些数据未在本次任务中独立核验，也不能单独证明节省来自某一个机制或适用于所有任务。
- **作者报告的演化过程**：18 个版本、22 小时，以及角色、策略和工具用法的“涌现”。正文同时明确有人类参与发现问题和固化机制；不能据此宣称实现了完全无人参与的自我改进。
- **未核验的比较**：九类漏洞长链案例和 V-Mesh 白皮书约 29.5% 成功率缺少本次可检查的原始实验与同口径对照，不作为验收基线。
- **思想框架**：“女娲测试”“文明”“模型智力远超个体人类”等是作者提出的主张或类比；竞赛成绩不等于通过文中高级阶段，也不是 AGI 的实验证明。
- **未来设想**：双 harness 竞争演化和“示踪剂”是探索方向。原文明确示踪剂尚未加入开源版本，并提出可拆除、可栽赃等问题；本文不把它作为现有能力或实施要求。若另行讨论，需单独处理授权、归因可信度和隐私。

## 今后设计或优化时的最小检查项

按当前问题选取相关项，不要求每次完整走流程：

1. 当前瓶颈是什么？增加一个角色、规则或服务，预期改善哪项可观察结果？单 Agent 或更简单的实现是否已经足够？
2. 哪些状态必须跨会话保存？权威来源在哪里？能否从摘要下钻到证据，并纠正错误结论？
3. 某个 Agent 退出或压缩后，接班者能否避开已失败路径并接续任务？如何验证？
4. 谁决定策略，谁负责执行，谁维护运行？是否出现重复调度、重复恢复或多个状态权威？
5. 如何区分有进展、暂时等待、基础设施故障和需要用户决策？恢复成功的证据是什么？
6. 资源投入是否匹配任务难度？共享经验是否减少了重复探索和无关上下文？
7. 什么结果会推翻本次优化假设？用最小且可比较的验证，再决定是否保留复杂度。
